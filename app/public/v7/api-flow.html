How Eat talks to the server

Log a coach plan food on the phone. On the right, every step appears as it happens: what the phone works out on its own, the API request, what the server does, the response, and what changes on screen. Foods from several options of one meal can be logged together.

The phone's score, its +x% step, the line under it and the macro tiles follow the new logic: the same numbers as the panel.

What changes in the system

From reading the current repos (MyTatvaCore, MyTatva-Coach-React, app.goodflip.in, MyTatva-RN).

WhereTodayNew
Plan storageEach plan food stores food id, quantity and unit. Macros are looked up per food on every read.When the coach saves, the server stores each food's kcal, protein, carbs, fats, its share of its option, each option's totals, and each meal's share of the day.
Plan editsOverwrite the same plan.Saved as a new plan version. Each day is scored against the version active that morning.
Plan read on EatThree calls; foods carry calories only.One call, GET /v9/diet/day, with the plan (macros, shares, version), the day's logs and the score. Cached by plan version.
LoggingOne request per ticked food. Snap and voice logs are not linked to the plan.One request for everything in the bar, POST /v9/diet/logs, any options mixed. Snap and voice match foods to the plan where they can.
ScoreDoes not exist.Worked out on the phone for an instant preview and by the server on every write. Every write returns the same score block.
Line under the scoreNone.Chosen from the score block (went up, up only, no change, dropped) and filled from a template.
End of dayNo job.One scheduled job saves the day's score as final for Trend.
Coach portalShows the average option as Actual Calories.Also shows each meal's target and flags an option about twice or half the size of the others before assigning.
